The decoder's deadline

A quantum error-correcting code produces a new batch of check results every cycle. A classical decoder has to turn each batch into a decision, on time, for as long as the computation runs. This page lets you set the clock and the decoder and see what happens.

What the model does

One round of check results arrives every cycle time. Each decoder needs a fixed time to process one round, and several decoders can work on different rounds at once. If the decoders' combined capacity is at least the rate at which rounds arrive, the queue stays empty. If it is lower, the queue grows by the same amount every round and never recovers. Nothing is hidden in that: it is arithmetic, and it is why a decoder is judged by whether it keeps up with the clock and not only by how accurate it is.

Latency and throughput are different. Latency is the time from a round arriving to its answer. A decoder can have a latency of many cycles and still keep up, because it works on later rounds while earlier ones finish. Latency matters for how long a logical operation has to wait. Throughput decides whether the queue grows.

A real device, for scale

Google Quantum AI reported a distance-5 surface code run with a real-time decoder at an average latency of 63 microseconds, for up to a million cycles, with a cycle time of 1.1 microseconds. The latency is about 57 cycles, and the run kept up, so the decoder was evidently working on several rounds at once. The set-up above shows how the two numbers fit together.

What this leaves out

Real decoders split the data into windows that overlap, handle bursts of errors unevenly, and run on specialised hardware. The queue here is the simplest one: a constant arrival rate and a constant service time. It shows the deadline, not the engineering of any one decoder.
